Architectures API ​

Use array_adapter(arch) for backend adaptation and KernelAbstractions.get_backend(array) for kernel execution. A grid stores its execution architecture in grid.arch.

The declared shared _neumaier_sum(f, ks, T) helper returns (sum, compensation); add the pair to obtain the total. It evaluates terms in the order of ks in precision T. Convection and non-core Analysis import it explicitly; src/README.md declares sharing without adding an export.

AtmosTransport.Architectures Module
julia
Architectures

Execution architectures and their optional runtime integration.

An architecture is part of a grid's type-level model contract: CPU() selects host execution, while GPU(:cuda), GPU(:rocm), and GPU(:metal) select a concrete GPU runtime. The same object controls array adaptation, device synchronization, and runtime validation, so grid metadata cannot diverge from model storage.

AtmosTransport.Architectures.AbstractPointOp Type
julia
AbstractPointOp

A unit of work applied independently at every index of its index space. A concrete operation is a small isbits struct of integers and flags; the arrays it reads and writes travel in a shared context ctx (usually a NamedTuple). It defines two methods:

julia
index_space(op, ctx) -> NTuple{N, Int}
apply_point!(op, ctx, I::Vararg{Int, N})   # @inline; one index, no return value

launch!(op, ctx, backend) runs it as one kernel on a device and as a loop over the same body on the host, where bound_context(op, ctx) may first resolve loop-invariant lookups (an operation with much work per index can run the kernel on the host instead, see host_parallel). Operations compose by type:

  • Fused(ops...): independent operations in one launch. A trailing slot index selects the operation; indices outside an operation's own space are skipped. The operations run concurrently on a device and one after the other on the host, so they must write pairwise-disjoint cells, and no operation may read a cell that another one writes.

  • Sequence(ops...): dependent operations, launched in order (stream order on a device) with one synchronization at the end.

Fusing changes only the launch structure. For operations that satisfy the Fused contract, every index runs the same arithmetic on the same inputs, so results equal those of separate launches bit for bit.

AtmosTransport.Architectures.Fused Type
julia
Fused(ops::AbstractPointOp...)
Fused(ops::Tuple)

Independent point operations of equal index rank in one launch, over the elementwise-largest index space plus a trailing slot index. At least one operation is required.

On a device the operations run concurrently; on the host they run one after the other. The operations must therefore write pairwise-disjoint cells, and no operation may read a cell that another fused operation writes. Under this contract both paths give the results of separate launches bit for bit.

source
AtmosTransport.Architectures.FusionPolicy Type
julia
FusionPolicy

How a backend launches a Fused set of point operations, chosen by fusion_policy(backend): FuseLaunches() (the default) runs them as one kernel; SeparateLaunches() launches each operation over its own index space on its bound_context (operations that define one, such as the halo fills, then see their arrays directly), one after another, with one synchronization at the end. Results are the same either way (fused operations write disjoint cells and read none that another writes); which is faster depends on the backend.

AtmosTransport.Architectures.HostMemoryModel Type

HostMemoryModel

Whether host code can read and write a backend's device buffers directly, chosen by host_memory_model: DiscreteHostMemory() (the default: device memory is reached only through copies, as on CUDA and ROCm) or UnifiedHostMemory() (one memory that host and device share, as Metal's shared-storage buffers on Apple silicon; see host_mapped_vector).

AtmosTransport.Architectures.LinearCopy Type
julia
LinearCopy <: AbstractPointOp

At linear index i, ctx.dest[k][i] = ctx.src[k][i] for every array pair k of the tuples ctx.dest and ctx.src that has an element i: a set of copies as one launch over the longest array. The host runs the pairs as copyto!s. See copy_arrays!.

AtmosTransport.Architectures.copy_arrays! Method
julia
copy_arrays!(dest::Tuple, src::Tuple) -> dest

copyto!(dest[k], src[k]) for every pair of equally sized arrays. When every array of dest and src lives on one backend (single_launch_copy), all pairs are copied by one LinearCopy launch, queued on the current task's device queue without a host synchronization; the host backend copies each pair with copyto!. A batch that mixes backends (a host window uploaded to the device, or arrays on different devices) keeps one copyto! per pair.

The single launch applies to every device backend (CUDA, ROCm and Metal), not only to Metal: it replaces a batch of copies by one launch, and copies values unchanged, so the result equals that of the copyto!s bit for bit. On CUDA and ROCm a device-to-device copyto! is already queued asynchronously, so the gain there is fewer launches. On Metal it also removes host synchronizations: Metal.jl synchronizes the queue before every device-to-device copyto! and waits for its blit, so the 18 panel copies of a cubed-sphere flux refresh cost about 2.5 ms per step on an M5 Pro.

AtmosTransport.Architectures.fusion_policy Method
julia
fusion_policy(backend) -> FusionPolicy

FuseLaunches() unless a backend extension says otherwise (Metal launches separately: measured on an M5 Pro, a C90 packed-tracer halo exchange takes 1.1–1.3 ms with separate launches of bound arrays and 1.7–2.0 ms fused, while on CUDA the fused launch is 3–9× faster).

AtmosTransport.Architectures.host_mapped_vector Method
julia
host_mapped_vector(T, n, reference_array) -> (host::Vector{T}, device)

A device vector of n elements of type T on the backend of reference_array whose memory host code reads and writes through host, an Array aliasing the same bytes (no copies in either direction). Defined for backends with UnifiedHostMemory only. Host writes are seen by device work queued afterwards; device writes by the host after a synchronization (synchronize_storage!), which must also separate device reads from later host writes. host does not keep device alive: hold on to device as long as host is used.

AtmosTransport.Architectures.host_memory_model Method
julia
host_memory_model(reference_array) -> HostMemoryModel

The HostMemoryModel of the backend that holds reference_array (or the first panel of a tuple): UnifiedHostMemory() where a backend extension declares it (Metal), DiscreteHostMemory() otherwise. Callers dispatch on it to stage host data without a copy where the memory is shared.

AtmosTransport.Architectures.host_parallel Method
julia
host_parallel(op) -> Bool

How launch! runs op on the host (KernelAbstractions' CPU backend): false (the default) runs plain loops in one thread, the fastest choice for light operations such as halo fills; an operation with much work per index (a column walk) returns true to run the device kernel, which the CPU backend spreads over the Julia threads. A Fused set runs as one kernel if any of its operations does; under the Fused contract both paths give the same results.

AtmosTransport.Architectures.launch! Method
julia
launch!(kernel, backend, workgroup, ndrange, args...; sync = true)

Run the KernelAbstractions kernel (a @kernel function) on backend with workgroup over ndrange, then synchronize(backend) unless sync = false (several launches on one backend can share one synchronization). Kernel launches are being moved onto this helper module by module, so that workgroup choices and synchronization are explicit at each call site; the cubed-sphere advection sweeps keep their own profiled launch, which skips the host synchronization on GPU.
