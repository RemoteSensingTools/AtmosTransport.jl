Methods and data

How the timings were measured, what each number means, and the caveats per device.

Protocol

  • Runs. Forward cubed-sphere transport driven by real MERRA-2 meteorology on 72 levels (GCHP-matched preprocessing, dry basis), Float32, starting 2021-12-01, 8 simulated days per run. The binaries hold 7 days (C24–C180); simulated day 8 reuses the binary of day 3. C360 and C720 binaries hold 2 days and are cycled the same way; C720 uses GEOS-FP-derived binaries.
  • Steady time. The wall time of each simulated day is recorded; the steady value is the median over days 3 and later, so compilation (day 1) and warm-up (day 2) are excluded.
  • Passes. Every configuration of the release and operator matrices runs twice (the main-only scaling runs once). Within a pass the versions are interleaved (v0.5.0, v0.6.0, main for each configuration), and the second pass starts after the first, so slow drifts of the machine load hit all versions alike. The site shows the mean of the passes and both pass values; configurations whose passes differ by more than of their mean are flagged (Δ in tables, † in charts).
  • Output writing off ([output] enabled = false): the timings cover met input, the operators and time stepping.
  • Tracers. 1 = the protocol CO2 tracer; 4 = the protocol tracer set; 12 adds surface-flux tracers.
  • Operator sets. none = met input and time stepping only; adv, diff, conv = that operator alone; adv+emis = advection with surface fluxes (and decay); all = the full protocol run. Surface fluxes need advection, so there is no emissions-only set.
  • Matrices per device. Release: 3 versions × C24, C48, C90, C180 × 1 and 12 tracers × none, adv, all. Operator breakdown: 3 versions × C90, C180 × 12 tracers × diff, conv, adv+emis. Scaling (main): C24–C180 × 4 tracers × adv, all, plus C360/C720 where data and memory allow.

Metrics

s/day
steady wall-clock seconds per simulated day (lower is faster).
SYPD
simulated years per wall-clock day = 86400 / (365 × s/day) (higher is faster).
Speedup
s/day(old) / s/day(new); above 1 means the newer code or the device is faster.
Cells
6 N² × 72 levels for grid CN.
Cost per cell and tracer
s/day / (cells × tracers), in nanoseconds per simulated day. The time step changes with the grid, so this is per simulated day, not per step.
Input-bound
the none run takes at least of the time of the selected operator set.
Breakdown
input floor = none; advection = adv − none; diffusion = diff − none; convection = conv − none; emissions = (adv+emis) − adv; interaction / rest = all − (none + the four costs). Differences of noisy timings can be negative and are shown as they are.
Peak memory
GPU runs: peak device memory reported during the run; CPU runs: peak resident memory of the Julia process.

Code under test

Julia 1.12.6 (the lab machines' pinned version). Each version runs from its own worktree with the project's Manifest.

Devices and caveats

Input-bound grids (listed per device above, and marked on the Scaling page) are limited by met reading, kernel launches and host-side stepping rather than by the operators, so their speed says little about the kernels.

Data

  • records.csv: every timing record of every device as collected (including failed and repeated runs).
  • configs.json: what the site plots: one entry per device, version, grid, tracer count and operator set (mean, passes, spread, SYPD, cost, memory), the breakdowns and the failed runs.

Where several records exist for the same configuration and pass, the latest successful one is used.

Reproduce

  1. Timing harness (lab copy, not yet in the repository): run_timing.sh → timing.py, benchmark.jl. Point ATMOSTR_TIMING_REPO at the worktree of the version under test (each worktree needs a copy of the untracked Manifest.toml).
  2. Collect the records of each device into <data>/<device>/records.csv (schema in benchmarking/site/README.md).
  3. Build: python3 benchmarking/site/build_site.py --data <data> --out <folder>.
